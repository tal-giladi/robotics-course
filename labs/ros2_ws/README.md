# labs/ros2_ws — the karmel ROS 2 workspace (Jazzy)

Everything ROS 2 in the course: the robot description, the simulation, the controllers, SLAM,
navigation, and two ways to drive the real robot. Runs in the course Docker image
([`labs/docker`](../docker/README.md)) or on native Ubuntu 24.04 + ROS 2 Jazzy.
What was verified, and how: [TESTED.md](TESTED.md).

## Packages

### Frames and topics (both the simulation and the real robot)

```text
map ─(slam_toolbox / AMCL)─▶ odom ─(diff_drive_controller | base_node | EKF)─▶ base_footprint
base_footprint ─▶ base_link ─▶ left_wheel, right_wheel, caster_link, imu_link, laser,
                               camera_link ─▶ camera_optical_frame, range_front_link
```

| Topic | Type | Notes |
|---|---|---|
| `/cmd_vel` | `geometry_msgs/TwistStamped` | Jazzy's diff_drive_controller only accepts **stamped** twists. Stamp them with the current time |
| `/odom` | `nav_msgs/Odometry` | wheel odometry, `odom` → `base_footprint` |
| `/joint_states` | `sensor_msgs/JointState` | wheel angles |
| `/scan` | `sensor_msgs/LaserScan` | frame `laser` |
| `/imu` | `sensor_msgs/Imu` | frame `imu_link` (sim) |
| `/camera/image_raw`, `/camera/camera_info` | `sensor_msgs/Image`, `CameraInfo` | frame `camera_optical_frame` (sim) |
| `/battery_state`, `/range/front`, `/diagnostics` | | karmel_base only |
| `/odometry/filtered` | `nav_msgs/Odometry` | EKF (`use_ekf:=true`) |

Odometry attaches to `base_footprint` (the URDF root), not `base_link`: a TF frame has exactly one
parent, and `base_link` already has one.

## Build

```bash
cd ~/labs/ros2_ws                  # in the Docker dev container; natively: labs/ros2_ws
source /opt/ros/jazzy/setup.bash
rosdep install --from-paths src --ignore-src -y     # native installs only; the image has everything
colcon build --symlink-install
source install/setup.bash
colcon test && colcon test-result --verbose          # unit tests + linters
python3 check_config_sync.py                          # after editing labs/config/karmel.yaml (--fix copies it)
```

After changing `labs/config/karmel.yaml`, also update the matching values in
`karmel_bringup/config/controllers.yaml` and `nav2_params.yaml` — `colcon test` fails until you do.

Use your own `ROS_DOMAIN_ID` (e.g. `export ROS_DOMAIN_ID=17`) so other ROS systems on the network
cannot drive your robot.

## Simulation (Gazebo Harmonic)

```bash
# Gazebo + robot + bridge + controllers — the normal entry point
ros2 launch karmel_bringup robot.launch.py sim:=true world:=apartment x:=-1.5 y:=-0.5 rviz:=true

# no GUI (Docker without a display, CI, slow laptops); enable_camera:=false saves the most CPU
ros2 launch karmel_bringup robot.launch.py sim:=true headless:=true world:=apartment enable_camera:=false

# Gazebo + spawn + bridge only, no controllers (lessons 06.03–06.05)
ros2 launch karmel_gazebo sim.launch.py world:=tabletop
```

Worlds: `empty`, `apartment` (living room, bedroom, kitchen; doors ~0.8 m; a dining table the LiDAR
only sees the legs of), `tabletop` (low table with a red cube, green cylinder, blue sphere and yellow
box, 0.8 m ahead of the spawn point). Edit the apartment in `generate_apartment.py`, then
`python3 generate_apartment.py --map ../../karmel_bringup/maps > apartment.sdf`.

## Teleop

`teleop_twist_keyboard` 2.4 on Jazzy publishes `TwistStamped` with `stamped:=true` (verified in its
source: `stamped` and `frame_id` parameters). No `twist_stamper` relay is needed:

```bash
ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -p stamped:=true -p frame_id:=base_link
```

One-off command from the shell (runs until Ctrl-C; the controller stops the robot 0.5 s after the
last message):

```bash
ros2 topic pub -r 10 /cmd_vel geometry_msgs/msg/TwistStamped "{twist: {linear: {x: 0.2}, angular: {z: 0.5}}}"
```

## SLAM

```bash
ros2 launch karmel_bringup robot.launch.py sim:=true world:=apartment x:=-1.5 y:=-0.5
ros2 launch karmel_bringup slam.launch.py rviz:=true             # use_sim_time:=false on the real robot

```

## Navigation (Nav2)

```bash
ros2 launch karmel_bringup robot.launch.py sim:=true world:=apartment x:=-1.5 y:=-0.5
ros2 launch karmel_bringup navigation.launch.py initial_pose:=true x:=-1.5 y:=-0.5 rviz:=true
ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose \
  "{pose: {header: {frame_id: map}, pose: {position: {x: -1.8, y: 0.3}, orientation: {w: 1.0}}}}"
```

The default map is the ground-truth `karmel_bringup/maps/apartment.yaml` (map frame = Gazebo world
frame, so spawn pose = initial pose). Your own map: `map:=$HOME/maps/my_room.yaml`. Without
`initial_pose:=true`, set the pose with RViz's *2D Pose Estimate*. Controller: Regulated Pure
Pursuit, max 0.3 m/s — the reasoning is at the top of `config/nav2_params.yaml`.

## Real robot, path 1: `karmel_base` (no ros2_control) — lesson 04.16

On the Raspberry Pi, with the Pico on USB:

```bash
ros2 launch karmel_base base.launch.py                       # port = serial.device in karmel.yaml
ros2 launch karmel_base base.launch.py port:=/dev/ttyACM1 publish_tf:=false   # EKF publishes odom TF
```

`base_node` subscribes `/cmd_vel` (TwistStamped; `use_stamped_cmd_vel:=false` for plain Twist),
limits speed and acceleration, sends `V` commands at 50 Hz (feeding the Pico watchdog), stops after
0.5 s without commands, publishes `/odom`, TF, `/joint_states`, `/battery_state`, `/range/front`,
`/diagnostics`, and reconnects when the USB cable comes back.

Without hardware — a fake Pico on a pseudo-terminal (Linux/Docker):

```bash
ros2 run karmel_base fake_pico --link /tmp/ttyKARMEL        # terminal 1
ros2 launch karmel_base base.launch.py port:=/tmp/ttyKARMEL   # terminal 2
```

or over TCP with the cross-platform fake Pico from `labs/python` (also works on Windows):

```bash
python -m robotlab.fake_pico --port 5760                     # from labs/python
ros2 launch karmel_base base.launch.py port:=socket://localhost:5760
```

`fake_pico` fault injection: `--corrupt-rate 0.05`, `--disconnect-after 10 --reconnect-delay 3`.

## Real robot, path 2: ros2_control (`karmel_hardware`) — lesson 08.12

The same `robot.launch.py`, with one argument flipped:

```bash
ros2 launch karmel_bringup robot.launch.py sim:=false                          # /dev/ttyACM0
ros2 launch karmel_bringup robot.launch.py sim:=false serial_device:=/tmp/ttyKARMEL   # fake Pico
ros2 control list_hardware_interfaces
```

`sim:=false` renders the URDF with `karmel_hardware/KarmelSystem`, starts `ros2_control_node` and the
same `joint_state_broadcaster` + `diff_drive_controller` as in simulation. The LiDAR, camera and IMU
drivers (`sllidar_ros2` for the RPLIDAR C1, `v4l2_camera`, `bno055`) are started by their own lessons.

## Known limitations

- The simulated front range sensor is not modelled (no `sensor_msgs/Range` in Gazebo); the frame exists.
- The EKF config fuses wheel odometry + gyro only; tuning covariances is a lesson exercise.
- Under CPU-only rendering the simulation runs below real time (RTF 0.3–0.9 on the test machine); all
  nodes use `/clock`, so results are correct, just slower.
- Nav2 parameters were verified in simulation only; on the real robot expect to tune the RPP
  lookahead and the inflation radius (lesson 12.08).
