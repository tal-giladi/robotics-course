# 01.05 — Set up the Pico microcontroller and talk to it over USB

## What you will learn

- Flash the MicroPython firmware for the Raspberry Pi Pico 2 (RP2350) from the Pi, with no monitor and no laptop.
- Find the Pico on the Pi's USB bus, read what state it is in, and fix "permission denied" with the `dialout` group.
- Use `mpremote` from the Pi to open the REPL, run a script from the Pi's disk, copy files to the Pico and make a program start at power-up.
- Check your chip's stepping for erratum RP2350-E9 and read the chip's internal temperature sensor.
- Diagnose "Pico not detected" systematically, from cable to driver to permissions.

## Why it matters

The Pico 2 is the half of karmel that touches the physical world: from 01.08 on it drives the motors, counts the encoders
and runs the watchdog that stops the robot when the Pi goes quiet. Before you connect anything to its pins, you need a
reliable development loop: edit a file on the Pi, run it on the Pico in a second, see the output, stop it with Ctrl-C.

Doing this from the **Pi** (over SSH) rather than from your laptop is deliberate. It's exactly the path the robot uses
when it drives: the Pi talks to the Pico over USB serial. If `mpremote` works from the Pi, the protocol in 01.10 will
work too, and you'll never have to unplug the Pico from the robot to update its firmware.

## Concept

### Firmware, runtime, program

A microcontroller has no operating system and no disk in the usual sense. It has flash memory, RAM and pins, and it runs
exactly one program from power-on. **MicroPython** is that program: a small Python interpreter plus a tiny filesystem,
compiled for the RP2350 chip. You install it once, like installing a runtime on a server. After that, your `.py` files
are data that MicroPython reads and executes.

| Concept | Server analogy | On the Pico 2 |
|---|---|---|
| Install the runtime | Install .NET / Python on a VM | Copy `RPI_PICO2-…-v1.29.0.uf2` onto the Pico's boot drive |
| Interactive shell | `python` / `dotnet fsi` | The MicroPython **REPL** over USB serial |
| Remote execution and file copy | `kubectl exec`, `kubectl cp` | **`mpremote`**: `run`, `exec`, `fs cp`, `mount` |
| Service that starts at boot | a systemd unit | `main.py` in the Pico's filesystem |
| Network endpoint | TCP port | **USB CDC serial port**: `/dev/ttyACM0` on the Pi |

### Three states of a Pico

1. **BOOTSEL mode.** Hold the white **BOOTSEL** button while plugging in USB. The chip's built-in boot ROM presents a
   USB drive called `RP2350`. Copying a `.uf2` file onto it writes that file to flash and reboots. You can't break this
   mode with bad firmware; it's in ROM. This is your recovery path.
2. **MicroPython, idle.** The Pico appears as a USB serial port. You get a `>>>` prompt (the REPL).
3. **MicroPython, running a program.** Either a script `mpremote` sent (`run`) or `main.py` from flash, which starts
   automatically at power-up. Ctrl-C (which `mpremote` sends for you) interrupts it and returns to the REPL.

### One cable, two jobs

The micro-USB cable from the Pi carries **power** (5 V, from which the Pico makes its own 3.3 V) and **data** (a virtual
serial port). That's why a "charge-only" cable is the most common reason a Pico "doesn't work": the LED can be on while
no data wires exist.

> [!TIP]
> **Ask your teacher:** "Explain what happens, byte by byte, when I type `mpremote run hello_pico.py`: what does
> mpremote send over the serial port, what does MicroPython do with it, and how does the output come back?"

### Level 1 — The Pico 2 board in one table

| Feature | Value | Why you care |
|---|---|---|
| Chip | RP2350A, two Arm Cortex-M33 cores (or two RISC-V cores, selectable) at 150 MHz | Use the **Arm** MicroPython build |
| Logic level | **3.3 V** | Never put 5 V or battery voltage on a GPIO pin |
| Power | Micro-USB (VBUS, 5 V) → on-board 3.3 V switching regulator | Powered by the Pi's USB port on karmel |
| 3V3 pin output | Keep external load under **300 mA** | Powers encoders and I²C sensors (≈ tens of mA) |
| On-board LED | GP25 (on a Pico 2 **W**, the LED is `Pin("LED")`) | First blink test |
| Board-internal GPIOs | GP23 (regulator mode), GP24 (VBUS sense), GP25 (LED), GP29 (VSYS/3 on ADC3) | Don't use them for your own wiring |
| ADC pins | GP26, GP27, GP28 (+ internal temperature sensor on ADC channel 4) | Battery divider, current sense later |
| PIO | Programmable I/O state machines in hardware | Encoder counting in 01.09 |
| USB IDs | Vendor 0x2E8A; MicroPython 0x0005; RP2350 boot ROM 0x000F | How `find_pico.py` tells the states apart |
| Stepping | A2 (erratum RP2350-E9) or A3/A4 (fixed) | Decides whether internal pull-downs work |

### Level 2 — Practical: from blank Pico to a script run from the Pi

All commands run **on the Pi** over SSH (`ssh karmel`), unless marked otherwise.

> [!CAUTION]
> **Safety:** In this lesson the Pico is powered only by the Pi's USB port. Keep it off the robot's power wiring, and
> don't connect anything to its pins yet. Put it on a non-conductive surface (the breadboard or its foam) so the pins on
> the underside can't touch metal. When you probe pins with the multimeter (Step 9), hold the probe tip steady: slipping
> between the 3V3 pin and a neighbouring GND pin shorts the regulator.

#### Step 1 — Download the firmware onto the Pi

```bash
mkdir -p ~/firmware && cd ~/firmware
wget https://micropython.org/resources/firmware/RPI_PICO2-20260824-v1.29.0.uf2
ls -l RPI_PICO2-*.uf2            # about 700 KB
```

Get the current file name from https://micropython.org/download/RPI_PICO2/ (the "Releases" list, the Arm `.uf2`, **not**
`RPI_PICO2-RISCV-…` and not the Pico 2 **W** or original Pico builds).

#### Step 2 — Flash it from the Pi (BOOTSEL mode)

1. Hold **BOOTSEL** on the Pico and plug the micro-USB cable into one of the Pi's USB ports. Release BOOTSEL after one
   second.
2. The Pico is now a USB drive. Ubuntu Server doesn't mount drives automatically, so find and mount it:

   ```bash
   lsblk -o NAME,LABEL,SIZE,MODEL             # look for LABEL RP2350, SIZE about 128M
   sudo mount /dev/sda1 /mnt                  # use the device lsblk showed with LABEL RP2350
   ls /mnt                                    # INDEX.HTM  INFO_UF2.TXT
   cat /mnt/INFO_UF2.TXT                      # "Board-ID: RP2350" confirms the Pico 2 boot ROM
   sudo cp ~/firmware/RPI_PICO2-20260824-v1.29.0.uf2 /mnt/ && sync
   sudo umount /mnt 2>/dev/null || true       # the drive has already vanished: the Pico rebooted
   ```

3. Within a few seconds the Pico reboots into MicroPython. (On a laptop, the same step is drag-and-drop onto the
   `RP2350` drive.)

#### Step 3 — Find it

```bash
ls -l /dev/ttyACM*                                   # crw-rw---- 1 root dialout ... /dev/ttyACM0
ls -l /dev/serial/by-id/                             # usb-MicroPython_Board_in_FS_mode_<serial>-if00 -> ../../ttyACM0
sudo dmesg | tail -5                                 # cdc_acm ... ttyACM0: USB ACM device
python3 find_pico.py                                 # the script from the Code section
```

`/dev/ttyACM0` can become `ttyACM1` when other USB serial devices (a LiDAR in Stage 3) appear first. The
`/dev/serial/by-id/…` link contains the Pico's unique serial number and never changes; 03.03 turns it into a udev rule.

#### Step 4 — Permissions: the `dialout` group

`crw-rw---- root dialout` means only root and members of `dialout` can open the port. 01.04 added you; check:

```bash
groups | grep -o dialout || echo "NOT in dialout"
```

If it's missing: `sudo usermod -aG dialout $USER`, then **log out and log in again**. Don't `chmod 666 /dev/ttyACM0` or
run tools with `sudo`: the first is undone at every replug, the second teaches the robot's software to run as root.

#### Step 5 — Install `mpremote`

Ubuntu 24.04 refuses `pip install` into the system Python (PEP 668, see
[FL.10](../optional-foundations/linux-and-tools/FL.10-python-environments-ubuntu.md)). `pipx` installs command-line tools
in their own virtual environments:

```bash
sudo apt install -y pipx          # done in 01.04 if you followed it
pipx install mpremote
pipx ensurepath                   # adds ~/.local/bin to PATH; log out and in once
mpremote --version
mpremote connect list             # /dev/ttyACM0 <serial> 2e8a:0005 MicroPython Board in FS mode
```

#### Step 6 — The REPL

```bash
mpremote repl                     # connects to the first USB serial device; Ctrl-] or Ctrl-x to exit
```

Press Enter to see `>>>`, then try:

```python
>>> import sys
>>> sys.implementation
(name='micropython', version=(1, 29, 0, ''), _machine='Raspberry Pi Pico2 with RP2350', _mpy=...)
>>> from machine import Pin
>>> led = Pin(25, Pin.OUT)
>>> led.on()                      # the green LED lights
>>> led.off()
>>> import machine; machine.freq()
150000000
```

Keys inside the REPL: **Ctrl-C** interrupts a running program, **Ctrl-D** soft-resets MicroPython (clears variables,
reruns `main.py` if present), **Ctrl-E** enters paste mode for multi-line code.

#### Step 7 — Run scripts from the Pi's disk

`run` sends a file from the Pi to the Pico's RAM and executes it; nothing is written to the Pico's flash.

```bash
cd ~/robotics-course/labs/firmware/pico
mpremote run examples/01_blink.py          # LED blinks once per second; Ctrl-C stops it
cd ~ && mpremote run hello_pico.py          # the lesson's script: board, version, stepping, temperature, 5 blinks
mpremote exec "import os; print(os.uname())"
```

For scripts that `import` other modules from a folder (from 01.08 on), `mount` makes the Pico see that folder of the
Pi as its current directory, so edits on the Pi take effect at the next run without copying:

```bash
cd ~/robotics-course/labs/firmware/pico
mpremote mount . exec "import config; print(config.TICKS_PER_WHEEL_REV)"    # 2464
```

#### Step 8 — Files on the Pico and `main.py`

```bash
mpremote fs ls                                   # the Pico's flash filesystem (empty after a fresh flash)
mpremote fs cp ~/robotics-course/labs/firmware/pico/examples/01_blink.py :main.py
mpremote reset                                   # hard reset: main.py starts, the LED blinks
# unplug and replug the Pico: it blinks again with no mpremote involved
mpremote fs rm :main.py                          # mpremote interrupts main.py with Ctrl-C first
mpremote reset                                   # no more blinking
```

The `:` prefix means "on the device". This is how the karmel firmware is deployed in 01.10: its `main.py` starts at
every power-up and speaks the serial protocol.

#### Step 9 — Check the stepping (erratum E9) and the power pins

`hello_pico.py` prints the chip stepping. Write it down, and label the board if you have more than one:

- **A2** → erratum **RP2350-E9**: never rely on `Pin.PULL_DOWN`. Use pull-ups with active-low wiring, or an external
  pull-down ≤ 8.2 kΩ. karmel's pin plan already follows this ([01.01](01.01-plan-the-build.md), [FE.06](../optional-foundations/electronics/FE.06-pull-up-pull-down.md)).
- **A3 / A4** → fixed. Follow the same rule anyway, so your code works on any Pico 2 you swap in.

With the multimeter (DC volts, 20 V range, black probe on physical pin 38, GND):

| Red probe on | Physical pin | Expected |
|---|---|---|
| 3V3 (OUT) | 36 | 3.25–3.35 V |
| VSYS | 39 | ≈ 4.6–5.0 V (VBUS minus a diode drop) |
| VBUS | 40 | 4.75–5.25 V (the Pi's USB 5 V) |
| GP25 while the LED is on / off | (LED, not on the header) | measure GP15 instead after `Pin(15, Pin.OUT).on()`: 3.3 V / 0 V |

#### Step 10 (optional) — The same from your laptop

Plug the Pico into your laptop, install mpremote there (`pipx install mpremote` or `pip install mpremote` in a venv), and
run `mpremote connect list`. On Windows the Pico appears as `COM3`–`COM9`; `mpremote connect COM5 repl`. Only **one**
program can hold a serial port: close the laptop's `mpremote` before plugging the Pico back into the Pi.

### Level 3 — Mathematics: from ADC counts to a temperature

The RP2350 measures its own die temperature with a diode whose voltage falls as it warms. The datasheet gives
$V_{be} = 0.706$ V at 27 °C with a slope of −1.721 mV/°C. MicroPython's `ADC.read_u16()` scales the 12-bit reading to
0–65535, so

$$V = \frac{N}{65535} \cdot 3.3\ \text{V} \qquad T = 27 - \frac{V - 0.706}{0.001721}$$

**Example.** `read_u16()` returns $N = 14050$: $V = 14050 / 65535 \times 3.3 = 0.7075$ V, so
$T = 27 - (0.7075 - 0.706) / 0.001721 = 26.1$ °C.

How sensitive is it? One ADC step of the 12-bit converter is $3.3 / 4096 = 0.81$ mV, which is
$0.81 / 1.721 = 0.47$ °C. Add the 3.3 V reference's tolerance and the sensor's spread, and a reading within a few degrees
of room temperature (a bit above, the chip is working) is correct. This is your first taste of **sensor calibration**:
the formula is a nominal model, the real chip needs an offset (07.01).

**Why this matters for the robot:** the battery voltage in 01.14 goes through exactly this conversion, plus a resistor
divider. An error of 1% in the 3.3 V reference is 0.13 V on a 12.6 V pack, which is the difference between "low
battery" and "fine".

**Serial link speed.** The Pico's USB serial ignores the baud rate you set (115200 is a convention): data moves at USB
full speed, up to ~1 MB/s in practice. A 50-byte telemetry line at 50 Hz uses 2.5 KB/s (01.01).

### Level 4 — Implementation: what `mpremote` actually does

MicroPython's REPL has a machine-friendly mode called the **raw REPL**. `mpremote` uses it for everything:

1. It opens `/dev/ttyACM0`, sends **Ctrl-C** twice to interrupt whatever is running, then **Ctrl-A** to enter the raw
   REPL (no echo, no prompt).
2. For `run hello_pico.py` it sends the **file contents** followed by **Ctrl-D**. MicroPython compiles and executes it,
   streams `print` output back, and ends with a marker that separates normal output from an exception traceback.
3. `fs cp` writes files in small chunks through Python code executed on the Pico (`open(...).write(...)`), into the
   LittleFS filesystem in flash.
4. `mount .` installs a small virtual filesystem on the Pico whose `open`/`read` calls are served by `mpremote` over the
   same serial link.

Consequences you'll hit:

- **Only one owner per port.** If your robot program (or a stuck `mpremote repl` in another SSH window) has the port
  open, a second `mpremote` fails with "failed to access /dev/ttyACM0" or behaves oddly. Find it with
  `fuser /dev/ttyACM0` or `lsof /dev/ttyACM0`.
- **`run` doesn't reset the Pico** (by default mpremote keeps the interpreter state between commands). Use
  `mpremote soft-reset` when you want a clean slate, for example after changing a module you imported.
- **A hardware watchdog fights `mpremote`.** Once the karmel firmware enables `machine.WDT` (`HARDWARE_WATCHDOG_MS` in
  `config.py`), interrupting `main.py` stops it being fed, and the Pico resets seconds later. Leave it at `0` while
  developing ([labs/firmware/pico/README.md](../labs/firmware/pico/README.md)).
- **Boot order.** At power-up MicroPython runs `boot.py` (if present), then `main.py`. A `main.py` with an infinite loop
  and no way to interrupt still can be stopped: `mpremote` sends Ctrl-C. If even that fails (a crash loop), re-flash
  the `.uf2` from BOOTSEL; to also wipe the filesystem, Raspberry Pi publishes a `flash_nuke.uf2` for the Pico series.

## Code

### `find_pico.py` (runs on the Pi)

Finds Raspberry Pi USB devices and tells you the Pico's state by its USB product ID, including the BOOTSEL drive, which
has no serial port. Needs `python3-serial` (installed in 01.04). Save it in your home directory on the Pi.

```python
"""01.05 — find the Pico on the USB bus and say what state it is in.

Run on the Pi:   python3 find_pico.py          (needs: sudo apt install python3-serial)
Also works on Windows/macOS, where the serial port is COMx or /dev/cu.usbmodem*.

Raspberry Pi's USB vendor id is 0x2E8A. The product id tells you what is running:
  0x0005  MicroPython's USB serial (REPL)        -> ready for mpremote
  0x000F  RP2350 boot ROM (BOOTSEL, a USB drive) -> copy the MicroPython .uf2 onto it
  0x0003  RP2040 boot ROM (original Pico, BOOTSEL)
"""
from __future__ import annotations

import os
import sys
from dataclasses import dataclass
from pathlib import Path

RPI_VID = 0x2E8A
PRODUCTS = {
    0x0005: "MicroPython (USB serial REPL)",
    0x000F: "RP2350 BOOTSEL mode (USB drive, no serial port)",
    0x0003: "RP2040 BOOTSEL mode (USB drive, no serial port)",
}


@dataclass(frozen=True)
class UsbDevice:
    vid: int
    pid: int
    port: str | None      # serial device, if the device exposes one
    description: str


def serial_devices() -> list[UsbDevice]:
    try:
        from serial.tools import list_ports
    except ImportError:
        print("pyserial missing: sudo apt install python3-serial", file=sys.stderr)
        return []
    return [UsbDevice(p.vid, p.pid, p.device, p.description or "")
            for p in list_ports.comports() if p.vid is not None and p.pid is not None]


def sysfs_devices(root: Path = Path("/sys/bus/usb/devices")) -> list[UsbDevice]:
    """USB devices without a serial port (BOOTSEL drives) are only visible here, on Linux."""
    found = []
    if not root.is_dir():
        return found
    for dev in root.iterdir():
        try:
            vid = int((dev / "idVendor").read_text().strip(), 16)
            pid = int((dev / "idProduct").read_text().strip(), 16)
        except (OSError, ValueError):
            continue
        product = (dev / "product").read_text().strip() if (dev / "product").exists() else ""
        found.append(UsbDevice(vid, pid, None, product))
    return found


def classify(devices: list[UsbDevice]) -> list[str]:
    lines, seen = [], set()
    for d in devices:
        if d.vid != RPI_VID or (d.pid, d.port) in seen:
            continue
        seen.add((d.pid, d.port))
        state = PRODUCTS.get(d.pid, f"unknown Raspberry Pi product 0x{d.pid:04X}")
        where = f" on {d.port}" if d.port else ""
        lines.append(f"found {state}{where}  [{d.vid:04x}:{d.pid:04x}] {d.description}")
    return lines


def main() -> int:
    with_port = serial_devices()
    known = {(d.vid, d.pid) for d in with_port}
    # A MicroPython Pico appears in sysfs too; keep only sysfs entries without a serial port.
    devices = with_port + [d for d in sysfs_devices() if (d.vid, d.pid) not in known]
    lines = classify(devices)
    if not lines:
        print("No Pico found. Check: data-capable cable (not charge-only), `dmesg -w` while plugging in,")
        print("and whether the Pico's LED/BOOTSEL drive appears on another computer.")
        return 1
    print("\n".join(lines))
    if os.name == "posix" and any("/dev/tty" in l for l in lines):
        import grp
        if "dialout" not in {grp.getgrgid(g).gr_name for g in os.getgroups()}:
            print("warning: you are not in the dialout group -> sudo usermod -aG dialout $USER, then log out and in")
    return 0


if __name__ == "__main__":
    sys.exit(main())
```

### `hello_pico.py` (runs on the Pico, sent from the Pi)

Proves the whole chain: Pi → USB → MicroPython → chip peripherals. Save it on the Pi and run `mpremote run hello_pico.py`.

```python
# hello_pico.py - 01.05: prove the chain Pi -> USB -> MicroPython -> Pico hardware works.
#
# Run from the Pi without copying it to the Pico:
#     mpremote run hello_pico.py
# Expected: board name, version, CPU frequency, chip stepping, a temperature near room
# temperature, and the on-board LED blinking 5 times.

import sys
import time

import machine
from machine import ADC, Pin

board = sys.implementation._machine
version = ".".join(str(part) for part in sys.implementation.version[:3])
print("board          :", board)
print("micropython    :", version)
print("cpu frequency  :", machine.freq() // 1_000_000, "MHz")
print("unique id      :", machine.unique_id().hex())

if "RP2350" in board:
    # SYSINFO CHIP_ID register: bits 31..28 are the chip revision (see FE.06, erratum RP2350-E9).
    revision = (machine.mem32[0x40000000] >> 28) & 0xF
    steppings = {2: "A2 - has erratum E9: avoid internal pull-downs", 3: "A3 - E9 fixed", 8: "A4 - E9 fixed"}
    print("chip stepping  :", steppings.get(revision, "unknown (%d) - read the chip marking" % revision))

# ADC channel 4 is the RP2350's (and RP2040's) internal temperature sensor.
# Datasheet: Vbe = 0.706 V at 27 C, slope -1.721 mV per C.
sensor = ADC(4)
volts = sensor.read_u16() * 3.3 / 65535
print("chip temperature: %.1f C  (expect roughly room temperature +0..10 C)" % (27 - (volts - 0.706) / 0.001721))

led = Pin(25, Pin.OUT)   # Pico 2 on-board LED (on a Pico 2 W use Pin("LED", Pin.OUT))
for _ in range(5):
    led.on()
    time.sleep_ms(200)
    led.off()
    time.sleep_ms(200)
print("done: the LED blinked 5 times")
```

Both scripts were tested without hardware: `find_pico.py` against simulated sysfs entries and on a machine with no Pico;
`hello_pico.py` on CPython with stand-ins for `machine` (the MicroPython-specific calls are `sys.implementation._machine`,
`machine.mem32`, `machine.unique_id`, `ADC.read_u16` and `time.sleep_ms`, all in the MicroPython rp2 port).

## Expected result

- **01.05-E1:** (a) `found RP2350 BOOTSEL mode (USB drive, no serial port)  [2e8a:000f] RP2350 Boot` (the product
  string may differ slightly); (b) `found MicroPython (USB serial REPL) on /dev/ttyACM0  [2e8a:0005] Board CDC` or
  similar, with no dialout warning; (c) `No Pico found. …` and exit code 1. `mpremote --version` prints a version, and
  `mpremote connect list` shows `/dev/ttyACM0 … 2e8a:0005 MicroPython Board in FS mode`.
- **01.05-E2:** (1) The LED follows your commands. (2) `150000000`; a 16-hex-digit unique id; `gc.mem_free()` of a few
  hundred thousand bytes. (3) The prompt hangs, Ctrl-C prints `KeyboardInterrupt` and returns `>>>`. (4) After Ctrl-D the
  REPL prints `MPY: soft reboot` and `led` raises `NameError`.
- **01.05-E3:** (1) `board : Raspberry Pi Pico2 with RP2350`, `micropython : 1.29.0`, `cpu frequency : 150 MHz`, a
  stepping line (A2, A3 or A4), a temperature within ≈ 0–10 °C above room temperature, the LED blinking 5 times and
  `done: …`; warmed, the reading rises by a few degrees. (2) The LED blinks after a power cycle with no SSH; after
  `fs rm :main.py` and `reset` it stays dark, and `mpremote fs ls` no longer lists `main.py`. (3) 3V3 3.25–3.35 V,
  VSYS ≈ 4.6–5.0 V, VBUS 4.75–5.25 V.
- **01.05-E4:** (1) `mpremote` exits with a serial error; the Pico reboots on replug with no script running (a `run`
  script lives only in RAM). (2) The second command fails to get the port or garbles the first session: one owner per
  port. (3) Yes: `mpremote` sends Ctrl-C, which interrupts the loop, then `fs rm :main.py`. Only a program that disables
  interrupts or crash-loops needs BOOTSEL and a re-flash. (4) It works, running on the RISC-V cores, but the course
  firmware, its PIO timings and the datasheet notes assume the Arm build; re-flash the Arm `.uf2`. (5) GP26 is an ADC pin
  with an absolute maximum of IOVDD + 0.5 V = 3.8 V; 12 V destroys the pin and likely the chip. The battery goes through a
  divider (01.14) and is measured with a multimeter first.
- **01.05-E5:** 13600 → 0.6848 V → 39.2 °C; 14050 → 0.7075 V → 26.1 °C; 14400 → 0.7251 V → 15.9 °C. 40 °C needs
  $V = 0.706 - 13 \times 0.001721 = 0.6836$ V → $N = 0.6836 / 3.3 \times 65535 = 13{,}575$. With a 3.25 V reference the
  true voltage for $N = 14050$ is $0.6968$ V → 32.4 °C, so the 3.3 V assumption reads **6.3 °C low**. Small reference errors
  become big temperature errors because the slope is only 1.7 mV/°C.

## Troubleshooting

### Symptom: the Pico is not detected (no `/dev/ttyACM0`, `find_pico.py` finds nothing)

Work from the physical layer up, like debugging a network:

1. **Watch the kernel log while plugging in:** `sudo dmesg -w`, then plug the Pico in. Nothing at all → the Pi sees no USB
   device: go to 2. `usb … new full-speed USB device` but no `ttyACM` → go to 4.
2. **Cable.** Try another micro-USB cable known to carry data (one that works with a phone for file transfer). Charge-only
   cables are the #1 cause.
3. **Port and board.** Try another USB port on the Pi, then the laptop. Hold BOOTSEL while plugging in: if the `RP2350`
   drive appears, the board and cable are fine and the firmware is the problem.
4. **Firmware.** A device appears but no serial port → MicroPython isn't running (wrong `.uf2`, a crash loop, or a C
   program you flashed). Re-flash the Arm `RPI_PICO2` `.uf2` from BOOTSEL.
5. **Power.** The Pi reports under-voltage (`vcgencmd get_throttled` not `0x0`) → USB devices can drop out. Fix the Pi's
   supply first (01.04).

### Symptom: `Permission denied: '/dev/ttyACM0'`

1. `ls -l /dev/ttyACM0` → group `dialout`?
2. `id -nG` → does the **current session** list `dialout`? If `getent group dialout` lists you but `id -nG` doesn't, log
   out and back in ([FL.05](../optional-foundations/linux-and-tools/FL.05-permissions-users-groups.md)).
3. Don't fix it with `sudo mpremote` or `chmod`.

### Symptom: `mpremote` hangs, times out or prints `could not enter raw repl`

1. **Another program owns the port:** `fuser -v /dev/ttyACM0`. Close the other `mpremote repl`, your robot script or a
   `screen` session.
2. **A running program ignores Ctrl-C** (busy in a long blocking call, or the hardware watchdog resets the board):
   unplug and replug, then run `mpremote fs rm :main.py` immediately.
3. **Still stuck:** BOOTSEL + re-flash the `.uf2`. Your files on the Pico's filesystem survive a normal re-flash.

### Symptom: `mpremote: command not found`

`pipx ensurepath` changed your PATH for **new** logins: log out and in, or run `~/.local/bin/mpremote`. If `pipx` itself
is missing, `sudo apt install pipx`.

### Symptom: the BOOTSEL drive doesn't mount or the copy fails

1. `lsblk -o NAME,LABEL,SIZE` must show `RP2350`. If not, BOOTSEL wasn't held while plugging in.
2. `mount: wrong fs type`: you picked the disk (`/dev/sda`) instead of the partition (`/dev/sda1`).
3. The copy "fails" at the end with an I/O error: that's often just the Pico rebooting before `cp` finished its sync.
   Check with `find_pico.py`; if it shows MicroPython, it worked.

## Common mistakes

- **Downloading the wrong firmware.** `RPI_PICO` (original Pico), `RPI_PICO2_W` and `RPI_PICO2-RISCV` look alike. karmel
  needs `RPI_PICO2-<date>-v1.29.x.uf2` (Arm).
- **A charge-only USB cable.** The Pico's LED can blink from `main.py` while no data wires exist.
- **`sudo pip install mpremote`.** Blocked by PEP 668 on Ubuntu 24.04, and a bad idea anyway. Use `pipx`.
- **Leaving an `mpremote repl` open in another terminal**, then wondering why the next command hangs.
- **Using `Pin.PULL_DOWN` on an A2-stepping Pico 2.** Erratum E9 makes the input stick high. Use pull-ups.
- **Treating `/dev/ttyACM0` as a fixed name.** It moves when other USB serial devices appear. Use
  `/dev/serial/by-id/…` in configuration.
- **Copying a half-finished `main.py` with an infinite loop and the hardware watchdog on.** The board resets before you
  can remove it. Keep `HARDWARE_WATCHDOG_MS = 0` while developing.

## Knowledge check

1. What's the difference between `mpremote run script.py` and `mpremote fs cp script.py :main.py`?
   <details><summary>Answer</summary>

   `run` sends the file to the Pico's RAM and executes it once; nothing is stored, and a reset forgets it. `fs cp … :main.py`
   stores it in the Pico's flash filesystem as `main.py`, which MicroPython runs automatically at every power-up.
   </details>

2. `find_pico.py` reports `[2e8a:000f]`. What state is the Pico in, and what do you do next?
   <details><summary>Answer</summary>

   BOOTSEL mode: the RP2350 boot ROM is presenting a USB drive, with no serial port. Mount the `RP2350` drive and copy the
   MicroPython `RPI_PICO2` Arm `.uf2` onto it; the board reboots into MicroPython (`2e8a:0005`).
   </details>

3. You added yourself to `dialout` a minute ago, and `mpremote` still says permission denied. Why, and what's the fix?
   <details><summary>Answer</summary>

   Group membership is read at login; your current SSH session still has the old group list. Log out and back in (check
   with `id -nG`). Don't use `sudo` or `chmod` on the device.
   </details>

4. `read_u16()` on ADC channel 4 returns 13,800. What temperature is that?
   <details><summary>Answer</summary>

   $V = 13800 / 65535 \times 3.3 = 0.6949$ V; $T = 27 - (0.6949 - 0.706) / 0.001721 = 33.4$ °C.
   </details>

5. `hello_pico.py` prints `chip stepping : A2`. What must you avoid in your firmware, and what do you do instead?
   <details><summary>Answer</summary>

   Relying on internal pull-downs (`Pin.PULL_DOWN`): erratum RP2350-E9 lets pad leakage hold a released input near
   2.2 V, which the weak internal pull-down can't overcome. Use `Pin.PULL_UP` with active-low wiring, or an external
   pull-down of 8.2 kΩ or less.
   </details>

6. Debugging: `dmesg` shows a new full-speed USB device when you plug in the Pico, but no `ttyACM0` appears, and BOOTSEL mode works. What's wrong and how do you fix it?
   <details><summary>Answer</summary>

   Cable, port and board are fine (BOOTSEL works, a device enumerates). MicroPython isn't presenting its serial port:
   wrong firmware (RISC-V/Pico W/C program) or a crash. Re-flash the correct Arm `RPI_PICO2` `.uf2` from BOOTSEL.
   </details>

7. Predict: your robot program has `/dev/ttyACM0` open, and you run `mpremote fs ls` in another terminal. What happens, and what should you do?
   <details><summary>Answer</summary>

   Two programs fight over one serial port: `mpremote` may fail to enter the raw REPL, or it interrupts the firmware and
   the robot program sees garbage. Stop the robot program first (and stop the motors), then use `mpremote`. One owner per
   port.
   </details>
